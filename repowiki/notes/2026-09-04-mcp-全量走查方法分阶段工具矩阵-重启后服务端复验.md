## 背景

需要在新建的集中式 harness 工作区上从零走查 CodeWiki MCP 全部能力（约 40 个工具），产出结果矩阵并定位缺陷。

## 走查方法

**分阶段**（每阶段独立记录通过/失败，避免一处卡死全盘停摆）：

1. 初始化/登记：`init_workspace` / `add_workspace_repo` / `remove_workspace_repo`
2. 代码分析：`analyze_repo` / `analyze_workspace` / `analyze_impact` / `analyze_changes`
3. 组件：`list_components` / `list_dependencies` / `read_code_components`（模块级依赖需先 `save_module_tree`）
4. 文档生成链路：`get_prompt` → `save_module_tree` → `get_processing_order` → `write_doc_file` / `edit_doc_file` → `close_session` → `query_wiki`
5. 检索/笔记/质量：`query_wiki`（含 `mode=check`、`repo=` 过滤）/ `wiki_stats` / `ingest_note` / `batch_ingest` / `confirm_note` / `reject_note` / `batch_set_status`
6. 生命周期与来源：`ingest_source` / `retract_source` / `lint_wiki` / `flag_issue` / `stamp_evidence` / `review_changes`
7. 聚合：`consolidate_notes`（prepare+submit）/ `refresh_doctrine`（prepare+submit）
8. 任务记忆：`create_task` / `list_tasks` / `set_session_task` / `add_task_memory` / `get_task_context` / `compact_task_memories` / `complete_task` / `delete_task`
9. 对话：`capture_conversation` / `distill_conversation`（prepare → submit → 冲突 → dedup skip/skip）

**验收闭环**：离线跑 pytest 验证逻辑 → **提示用户重启 MCP**（Agent 无法代为重启，服务进程持有旧代码）→ 重启后在服务端重跑走查确认真实生效 → 每轮结束 `close_session` 重建索引并跑全量 `lint_wiki`。

## 实测经验

- `lint_wiki(checks=["all"])` 在较大语料上可能超时，可改跑 5 项子集定位。（后续查明真因是 `git_sync.sync_check` 阻塞事件循环，见相关笔记）
- `write_doc_file` 首次调用可能超时但**实际已落盘**，重放会报 `File already exists`；重放前先确认文件是否已存在。
- 走查会在 `repowiki/` 下留下 `*.lck` 锁文件（本轮 11 个，notes/wiki/.meta/telemetry 均有）。新生成的 `.gitignore` 第 31 行已含 `*.lck`，`git check-ignore -v` 可验证命中；若报警应先用 `git check-ignore` 实测，不要凭旧版 `.gitignore` 误判。
- 用探针笔记/探针页验证功能后必须清理并重建索引，否则会污染 `wiki_stats` 与 `lint_wiki` 结论。
- 留给人工的部分要显式说明：`watch_repo` 只测了 `status`（未启停线程）；`distill_conversation` 的 Mode A/B 需 LLM 回调或 `MAIN_MODEL`；`query_wiki` 的 `mode=overview/detail/directory` 与 `hop` 图扩展；`analyze_workspace(generate_repo_wikis=true)` 属重量级。
